静态站点本身不需要后端，但当你想做点赞、评论、作品数据统计，或者一个简单的创作后台时，还是需要一个薄薄的服务层。这篇记录我在个人项目里的接口与鉴权设计。

<!-- more -->

## 需求边界

先划清边界，避免过度设计：

- 公开读：文章、作品、栏目数据
- 登录写：新建 / 编辑内容、上传资源
- 轻互动：点赞、收藏（可选，需要防刷）
- 管理端：只对站长开放

个人项目不需要微服务，一个单体服务 + 一个数据库就够。

## 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | Node.js | 与前端技术栈一致，开发切换成本低 |
| Web 框架 | Fastify / NestJS | 前者轻量，后者适合结构化项目 |
| 数据库 | PostgreSQL | 关系清晰，JSON 字段也够用 |
| 缓存 | Redis | 会话、限流、热点数据 |
| 文件 | 对象存储 | 视频和图片不落应用服务器 |

## 接口设计

以资源为中心，统一前缀和返回结构：

```http
GET    /api/v1/posts             # 文章列表（分页、筛选）
GET    /api/v1/posts/:id         # 文章详情
POST   /api/v1/posts             # 新建（需登录）
PATCH  /api/v1/posts/:id         # 更新（需登录）
DELETE /api/v1/posts/:id         # 删除（需登录）
```

统一响应体，前端只写一次解析逻辑：

```ts
interface ApiResponse<T> {
  code: number;      // 0 表示成功
  message: string;
  data: T;
  requestId: string;
}
```

分页参数统一为 `page` / `pageSize`，返回 `total`，避免每个接口各写一套。

## 鉴权方案

个人站用「短生命周期访问令牌 + 刷新令牌」就够了：

1. 登录成功后签发 access token（15 分钟）和 refresh token（7 天，HttpOnly Cookie）。
2. access token 放在内存里，由前端请求头携带。
3. refresh token 只用于换新令牌，不参与业务接口。
4. 服务端维护刷新令牌白名单，支持主动踢下线。

```http
Authorization: Bearer <access_token>
```

::: warning 几个容易踩的坑
- 不要把 refresh token 存进 localStorage，XSS 一旦发生就等同于账号泄露。
- 管理接口必须做**服务端**角色校验，不能只靠前端隐藏按钮。
- 上传接口要校验文件类型与大小，不能信任客户端声明的 MIME。
:::

## 安全清单

- [x] 参数校验（Zod / class-validator）
- [x] 登录与敏感接口限流
- [x] 密码使用 Argon2 / bcrypt 哈希
- [x] CORS 只放行自己的域名
- [x] 错误信息不泄露堆栈
- [x] 数据库操作全部参数化

## 部署形态

单体服务 + 托管数据库 + 对象存储，一台小机器就足够。未来如果访问量上来，再考虑把读接口放到 CDN 或边缘缓存。

个人项目的后端目标不是「大而全」，而是**稳定、便宜、够用**。
