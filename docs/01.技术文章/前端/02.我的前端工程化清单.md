工程化不是一上来就堆工具，而是把「容易出错、又会被反复执行」的事情交给机器。下面是我在个人项目里长期保留的一份清单。

<!-- more -->

## 一、代码规范

| 关注点 | 工具 | 目标 |
| --- | --- | --- |
| JavaScript / TypeScript | ESLint | 统一语法与潜在错误检测 |
| 代码格式 | Prettier | 消灭格式争论 |
| Vue 单文件组件 | eslint-plugin-vue | 模板与脚本的规范检查 |
| 提交信息 | commitlint + cz-git | 生成可读的变更历史 |

原则只有一条：**规则要能自动修复，不能自动修复的规则要少而精**。

```bash
pnpm lint          # 全量检查
pnpm lint:eslint   # ESLint 修复
pnpm lint:prettier # Prettier 格式化
```

## 二、提交前检查

用 husky + lint-staged 把检查放到提交前，只检查本次改动的文件：

```json
{
  "lint-staged": {
    "*.{js,ts,vue}": ["eslint --fix", "prettier --write"],
    "*.{md,css,scss}": ["prettier --write"]
  }
}
```

这样既能在本地拦住问题，又不会因为全量检查拖慢提交。

## 三、持续集成

CI 里至少跑三件事：

1. 安装依赖（锁文件必须提交）
2. 类型检查与构建
3. 部署到预览环境

构建失败要能第一时间看到，而不是等发布之后才发现白屏。

## 四、性能与体验

- 图片统一压缩，优先 WebP / AVIF
- 长列表或重组件按需加载
- 字体使用 `font-display: swap`
- 交互元素保留键盘可访问性
- 为动态内容设置合理的骨架屏

## 五、可维护性

- 目录结构按「功能」而不是「文件类型」划分
- 公共逻辑抽成 composable，避免复制粘贴
- 配置文件集中管理，环境差异用环境变量表达
- README 写清楚「怎么跑起来」，比写架构图更重要

工程化的价值不在工具本身，而在于让每一次改动都更可预期。
